# Antigravity CLI 1.4.6: support statement

Scope: one exact route, `antigravity-cli/stream-json/1.4.6-stdout`: Antigravity CLI 1.4.6 in headless print mode
(`agy --print <prompt> --output-format stream-json`), raw standard output read by `CliCapture`, contract
`antigravity-cli/stream-json/1.4.6/0.2.0-prototype`, extension `agentic_cli` 0.10.0-prototype. Another version or route
is retained whole and not normalized until it has its own compatibility entry. The CLI updates itself; check
`agy --version` before relying on a capture.

The interface basis is the published headless and permissions documentation and the public CHANGELOG at tag 1.4.6,
reconciled with sanitized live recordings. No emitter source, typed schema or vendor test is published, so the inventory
is "documented plus observed" and its completeness is not established. The figures below are generated by
`MappingCatalogTest` (`CLI-COVERAGE.md`), `ParityLedgerTest` (`PARITY.md`) and `LiveScenarioTest` (`LIVE-SCENARIOS.md`)
in the TCK's `target/mapping-catalog/`; regenerate them rather than copying numbers forward.

## Normalized and checked

Of 44 catalog concepts, 21 are verified by the independent oracle on this route's recordings: session identity, prompt
submission (without text, which the stream does not carry), turn completion with status and response text, response
items in order, tool start identity, name, kind and exact arguments, result ownership and content, failure only where
`tool_info.error` is reported, reported states, usage components, reasoning token count, usage scope and finality,
permission decisions, launch settings, provenance, retention and reconstruction, and the time basis.

- **Identity.** A step is identified by its `step_index` (identity basis 99 Other, "Conversation step index") within its
  source artifact and conversation. Equal indices in another capture are other steps; continuity across a resumed
  process is not asserted.
- **Text.** Each `text_delta` fragment is a content block with `text_update_id` 1 Increment: a step's text is its
  fragments joined in order. The turn's own `result.response` is a separate whole text and is never concatenated with
  them. No provider response id is reported or invented.
- **Usage.** A step's own usage is stated at scope 99 Other, "Conversation step", as that step's total. One step is not
  established as one model invocation, so it is never stated as a model response's usage. The result's usage is the
  session's cumulative snapshot. It covers the steps and is never added to them, and it can exceed their sum: on an
  interrupted run it reported usage that no emitted step reports, and the stream does not say where it came from. Neither figure is derived from the other.

## Token accounting and cost

| Quantity | Status on this route |
|---|---|

| Uncached input | conditional: `input_tokens` excludes cache reads, but cache writes are not reported, so it is the uncached component's conditional value, never the canonical tranche |
| Inclusive input, cache writes | unavailable (no cache writes are reported) |
| Whether thinking is part of output | unresolved: no relation is stated, so no additive formula is assumed |

## Not normalized

- **Unavailable at source** (7 concepts): provider response and model-facing call ids, reasoning text, structured tool results,
  separate operations and their attribution, cost, model identity unless `--model` overrides it.
- **Retained only** (2 concepts): reported durations (step and result `duration_seconds`), and unresolved step families
  (`checkpoint`, `system_message` and unknown steps, kept whole). Also kept only in their records: tool names and
  parameters repeated on result records, `tool_info.error` (type and message) on a failed step that also reports output,
  `result.error`, `num_turns`.
- **Unsupported** (1 concept): child runs. A subagent spawn's `subagent_info`, including the child conversation id, is the spawn's
  result content. The child's own records are not in this stream.
- **Unresolved** (9 concepts, 6 of them pending on every CLI): injected context, session accounting, retained
  known-meaning families, API request attempts, payload size and truncation, session resume linkage, child-run metadata,
  context compaction, hook executions. Also unresolved for specific fields: whether thinking is part of output, and a
  command's exit status (rendered text only).
- **Unexercised** (4 concepts): redacted or encrypted reasoning, media, unknown block kinds, opaque or malformed records.
  The recordings also exercise no `--model`, `--agent` or `--json-schema` option and no parallel tools.

## MCP

MCP calls arrive as the dispatcher tool `call_mcp_tool`, whose parameters name `ServerName`, `ToolName` and `Arguments`.
They are kept exactly as the call's arguments and never lifted into a tool name or namespace. Two runs used the same
workspace MCP configuration (`<workspace>/.agents/mcp_config.json`), one per permission mode; each states only its own mode.

- **Default request-review mode, no `mcp` allow rule** (live recording `antigravity-live-1.4.6-mcp-denied`): the CLI
  auto-denied the `mcp` permission category, and its stderr said headless mode cannot prompt for it. The documented
  `permissions.allow` route (for example `mcp(<server>/*)`, which takes precedence over the mode) was not tried. The step went ACTIVE, then DONE with
  neither output nor error, so its outcome is not derivable. The result reports `denied_actions [{action: mcp}]` as a
  run-scope denial that names no step.
- **`--dangerously-skip-permissions`** (init `permission_mode` `always-proceed`; live recording
  `antigravity-live-1.4.6-mcp`): `call_mcp_tool` ran three times, at steps 2, 4 and 6. The two `echo_record` steps ended
  DONE with `tool_info.output` the server's own text content (`{"echo": "alpha", "n": 1, "ok": true}`, with spaces). The
  server also returned structuredContent and `isError` false; the stream reports neither, so the result is text only, and DONE alone does not establish success: the
  outcome stays not derivable. `always_fails` ended in state ERROR with `tool_info.output` and
  `tool_info.error {type TOOL_ERROR}`: the output is the result content, with `error_reported` true and status Failure
  (Reported); the error object is kept in the retained record. The calls have distinct step indexes, arguments and outputs, and each result is owned by its own step.
  The turn succeeded and nothing was denied.

Neither stream reports MCP initialization, discovery, resources, prompts or progress, and none is claimed.

## Live scenario coverage

Live-observed: normal response, built-in tools, repeated tools, tool failure, permission rejection (command and `mcp`
categories), MCP calls with text results and a tool error (under `--dangerously-skip-permissions`; blocked in the recorded
request-review run without an `mcp` allow rule), subagent spawn, interruption with a tool open, usage. Not run: rich content.
Repeated tools are not parallel proof, and a spawn is not the child's interior.
